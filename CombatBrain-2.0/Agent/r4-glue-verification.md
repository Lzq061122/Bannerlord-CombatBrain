## 3. 逐 CB 落地机制

### CB-001 战场状态底座（认知层 · 只读聚合）
- **读哪些**：`Mission.Teams` → 每 `Team.FormationsIncludingSpecialAndEmpty`（8 槽，含空） → 每 `Formation` 读 `CountOfUnits`、`QuerySystem.IsInfantryFormation/IsRangedFormation/IsCavalryFormation`、`Width`、`Direction`、`CurrentPosition`、`OrderPosition`、`CachedFormationIntegrityData.DeviationOfPositionsExcludeFarAgents`；敌我经 `Team.IsEnemyOf/IsFriendOf`（自反须 `team==mine` 旁路）。逐兵种数量：遍历 `formation.Units`/`UnitsWithoutLooseDetachedOnes` 累加 `QuerySystem.IsXFormation`；单兵 `Character`/`Equipment` 可只读（质量 tier 属 PoC）。
- **控制对象**：无（纯只读）。**运行阶段**：`OnDeploymentFinished` 起建初态，`OnMissionTick` 增量刷新。
- **冲突**：无写入，无原生覆盖风险。
- **拿不到的信息（明确列出）**：① 单兵精确 HP/士气/疲劳（宪章 §14 原就禁止，且 RTS 不可见）；② "Formation 职责"——这是 CB 自赋语义，引擎只给 `FormationAI.ActiveBehavior`（原生当前行为，仅可作观测）；③ 敌方未接敌方向之外的"意图"——只能从 `CurrentPosition`/`Direction` diff 推断（CB-011 范畴）；④ 干净的可行走性布尔（见 CB-013）。
- **证据强度**：VERIFIED。

### CB-002 指挥执行网关（执行层 · 唯一出口）
- **Route A（软注入）**：`formation.AI.AddAiBehavior(new MyBehavior())` + `formation.AI.SetBehaviorWeight<MyBehavior>(大权重)`；`MyBehavior : BehaviorComponent` 重写 `GetAiWeight()` 提权，引擎 `FindBestBehavior`（max-weight）选中后其 `CalculateCurrentOrder()`/`CurrentOrder` 成为该 Formation 的 MovementOrder。**仅表达 Movement 域**（Facing/Arrangement 不经 Behavior tick）。
- **Route B（硬接管）**：`formation.SetControlledByAI(false, enforceNotSplittableByAI)` 关原生 AI；IL 证实 `SetControlledByAI(false)` 只置 `IsAIControlled=false`，**且 `FormationAI.TickOccasionally` 在 `get_IsAIControlled==false` 时早退不写 Movement**【IL】。随后主线程 `OnMissionTick` 直接 `SetMovementOrder/SetFacingOrder/SetArrangementOrder/SetFormOrder/SetFiringOrder`。
- **主线程收敛**：所有写令只在 `OnMissionTick(dt)`（主线程）落地；原生 `doAsyncAITick→TickOccasionally` 跑 worker 线程，CB 绝不在此路径写编队。
- **玩家接管安全归还**：订阅 `OnFormationAIActiveBehaviorChanged`/`OnActiveBehaviorChanged`，检测 `IsAIControlled` 边沿（玩家 F1/F6 或阵亡触发），立即释放 Route B 短租约（fail-open）。
- **与原生 AI 冲突点**：① Route A 行为与原生 GOB 权重竞争（须高权重/续权）；② Route B 下**Facing/Arrangement 在 AI 关闭后是否仍被残留路径覆盖——未实机闭合（PoC）**；③ `OnBehaviorActivatedAux` 激活时会重设全命令（BetterPikes 对其打 HarmonyPatch 证实真实存在）。
- **是否需要关原生**：Route A 不需关（与玩家接管天然兼容）；Route B 需 `SetControlledByAI(false)` 短租约，到期/接管即归还。
- **无法控制的 Engine 行为**：原生每帧 Agent 定位/碰撞数学（native `AutoGenerated.dll`）；`ArrangementOrder` 有原生节流（见 R1 勘误"未获证实"项）。

### CB-003 决策节奏与指挥延迟（执行层 · 时间门控）
- **计时原语**：`Mission.Current.CurrentTime`（float 秒时间戳）、`MissionTimer`（可 `new MissionTimer(0.8f)` 作冷却/延迟，`Check()`/`Reset()`）、`MissionTime`（时间差量）。三者均【符+调】。
- **机制**：`MissionBehavior.OnMissionTick(dt)` 主线程每帧触发；高层规划按 `CurrentTime` 累积门控（每 N 秒一次），命令经 `MissionTimer` 延时错峰落地形成 Command Latency。ImmersiveBattlefields 以 `MissionTimer(0.8~12f)` 限流可作样板。
- **约束**：禁每帧 `SetArrangementOrder`（原生节流）；意图变化才落令。

### CB-013 地形/站位认知（认知层）
- **高度**：`Mission.Scene.GetGroundHeightAtPosition(pos, BodyFlags.CommonCollisionExcludeFlags)`【社 sig + 符】；`GetGroundHeightAndBodyFlagsAtPosition(pos, out BodyFlags, ...)` 额外给接触面标志【社+符】。RTSCamera/TAOM 实战调用证实可用。
- **可行走性/NavMesh**：**未找到** `IsWalkable`/`GetNavigationMeshFaceIndexAtPosition`/`NavMeshBody`；仅有 `NavigationMesh`/`PathFaceRecord`/`BodyFlags` 符号【符】。可行走性只能经 `BodyFlags` 位推断，位语义 PoC → EXPERIMENTAL 子项。
- **影响**：高度差 + BodyFlags 已满足 CB-013 主体（高地/站位优劣）；精细可行走性判定延至 PoC，不阻断主线。

### CB-014 战场观测与指令溯源观测器（独立于决策栈）
- **机制**：① 订阅 `Formation.OnAfterArrangementOrderApplied(Formation, ArrangementOrderEnum)`、`Team.OnFormationAIActiveBehaviorChanged(Formation)`、`FormationAI.OnActiveBehaviorChanged`——三者均在 ImmersiveBattlefields 中真实订阅【调】，覆盖敌/我/盟三队（IB 对 Player/Enemy/Ally 三队各订阅）。
- **独立溯源（关键）**：观测器**不读 CB 自身 Record**，而是逐帧记录 `Formation` 的 `MovementOrder`/`FacingOrder`/`ArrangementOrder`/`IsAIControlled`/`AI.ActiveBehavior` 当前值；当 CB 网关写入时打 CB 标记，否则按"IsAIControlled 真→原生 AI；假且非 CB 写入→玩家/其他"归类。这满足"独立于 CombatBrain 自身记录"的硬性要求，规避旧项目 `OrderTrace` 自证为伪的坑。
- **时间序列**：配合 `Mission.Current.CurrentTime` 记录关键指标（兵力、凝聚度 `CachedFormationIntegrityData`、位置）形成回归序列。

## 4. AI 队无 OrderController 的专项论证（全局最关键约束）

**结论：AI 队伍没有、也不可用 OrderController 发令。全引擎发令只走 Route A/B。**

最强本机证据链（ilscan 反汇编 `TaleWorlds.MountAndBlade.dll`）：
1. **OrderController 是 owner-Agent 绑定的玩家发令 UI 控制器**。`OrderController..ctor` IL【IL】将 `Ldarg_1→_mission`、`Ldarg_2→Team`、`Ldarg_3→Owner`（并 `Formation.set_PlayerOwner`）——构造即绑定一个 `Agent owner`（玩家主体）。其方法面 `SelectFormation`/`SetOrderWithFormation`/`SetOrderWithPosition`/`PlayOrderGestures`/`SimulateNewOrder*` 全是"玩家在地图上画命令"的语义，与 AI 编队指挥无关。
2. **Team 的 OrderController 仅两种索引**：`get_MasterOrderController = _orderControllers[0]`、`get_PlayerOrderController = _orderControllers[1]`【IL】。玩家队才有实质 OrderController；全反编译 Mod 源码中**零处**出现非玩家的 `.OrderController` 访问（grep `\.OrderOrderController\b` → 无匹配），所有 `PlayerOrderController` 用法均挂在 `Mission.PlayerTeam`/玩家队（RTSCamera `Patch_OrderTroopPlacer.cs:162,428`）。
3. **惰性建也是按 agent**：`Team.GetOrderControllerOf(Agent)` 对指定 agent `new OrderController(Mission, this, agent)`【IL】——再次印证 owner-agent 绑定，而非"给 AI 队一个发令器"。
4. **AI 实际发令路径与 OrderController 无关**：据 TAOM 反编译（`formations-and-team-ai.md`），AI 走 `TeamAIComponent → TacticComponent → BehaviorComponent.TickOccasionally → Formation.SetMovementOrder`，全程不经过 OrderController。Route A 即注入此管线的 Behavior/Tactic；Route B 直接 `Set*Order`。
5. **`SetCustomOrderController` 存在但非出路**：`Team.SetCustomOrderController(c1,c2)` 仅替换 `_orderControllers` 列表，传入物仍须是 `OrderController`（需 owner Agent）。其"对 AI 队生效"语义未验，且全 Mod 生态零使用——记为 PoC，但**不改变"AI 队发令走 Route A/B"的结论**。

> 推论：任何"给 AI 队 new 一个 OrderController 来发令"的设想，既无社区先例、又违背 owner-Agent 绑定语义、又在 IL 层面无引擎消费方。Route A/B 是唯一可靠路径。
