# CombatBrain 2.0 — 分阶段开发路线图 v0.1

> 状态：Draft，供评审。
>
> 上位目标：`Charter V0.2.md`。本路线图只规定开发顺序、阶段范围与验收门槛；不能改变 Charter 的目标和边界。
>
> 日期：2026-09-24。

## 1. 使用规则

1. 开发派单按 **Charter → 当前阶段 → 当前任务** 确定范围。阶段通过只表示本阶段目标已验证，不表示 Charter 最终目标已实现。
2. 每阶段必须交付可运行或可独立验证的结果。P0 是工程验证阶段，不宣称已形成 AI 决策闭环；P1 起才验证最小指挥闭环。
3. Exit Gate 必须有可复查的输入场景、运行构建身份、观测结果和判定记录。日志说明“CB 打算做什么”；战场状态与命令实际效果须由独立观测验证。证据不足记为 **未验证**，不能按通过处理。
4. P1 起保留已通过场景的回归，并至少增加与本阶段能力有关的对照或变化场景。P5 才扩大覆盖面，但不能把此前阶段建立在单一固定 Demo 上。
5. 阶段范围列出的 CB 编号仅用于对照现有《功能拆解草案》，不是批准该草案的全部设计。其 PoC 使用 **FD-PoC P1～P11** 标识，与本路线图 **P0～P6**、CBATH 的 **Phase 1** 区分。PoC 结论以实际实验为准。
6. Charter 的范围冻结、Formation 级边界、信息公平、不主动制造错误、Plan 与 Command 分离，从相关行为出现之日起持续生效。当前允许的完整战场信息以 Charter §14 所定义的 RTS Camera 类指挥视角为界，不沿用旧 CombatBrain 1.x 的信息口径。
7. CBATH 是验证工具，不是 CombatBrain 2.0 决策能力的完成证据。现有 CBATH Phase 1 已验证测试 Mod 自身身份、双方 Formation 快照及自动进入战斗；**尚未证明 CB2.0 已加载、能写令或可准确区分所有命令来源**。

## 2. 阶段总览

| 阶段 | 本阶段回答的问题 | 主要交付 | 进入下一阶段的关键证据 |
|---|---|---|---|
| P0 工程基座与可验证指挥 | CB2.0 实际加载了吗？读数可靠吗？发出的 Formation 命令真的生效了吗？ | 构建身份、共享战场状态、独立观测、最小命令通路 | 同一运行中的构建身份、状态读数与命令效果可独立核对；控制权交接安全 |
| P1 最小指挥闭环 | 状态变化能否形成不同的全军计划，并执行、观察和处理基本失效？ | 最小评价、Plan、任务、执行、基本反馈、决策节奏与延迟 | 对照场景产生不同且可追溯的计划；实际行动有最小反馈闭环 |
| P2 多 Formation 协同 | 多支部队能否围绕同一目标执行任务且不相互抢令？ | 通用任务分配、跨 Formation 协同、命令冲突裁决 | 多 Formation 行为与同一 Plan 一致；竞争命令按权限处理 |
| P3 反馈、止损与重规划 | 计划成功或失败后，AI 能否依据实际结果改变投入？ | 正负反馈、风险与战果评价、继续/调整/终止/重规划 | 正、负两类变化分别触发可解释的行动调整 |
| P4 主动权与战术博弈 | AI 能否主动改变局势，并依据对手反应调整后续计划？ | 有限试探、对手变化观测、机会利用 | 有反应与无反应对照证明调整来自观测，而非固定脚本 |
| P5 泛化与稳健性 | 同一决策机制能否处理不同战场，而不靠情形专用规则堆积？ | 场景矩阵、失效归因、必要的通用能力补足 | 关键场景覆盖及回归结果可复查，失败项有明确处置 |
| P6 Charter 最终体验验收 | 条件接近时，AI 是否能凭指挥能力对玩家构成实际威胁？ | 预先确定的实战验收方案、对照实验、行为审计 | 达到预定体验判据，且胜负原因与指挥决策相符 |

## 3. 阶段定义

### P0 — 工程基座与可验证指挥

**目标**：先证明“正在运行的是 CB2.0、它读到的状态可信、Formation 命令能落地”。本阶段的测试命令可以由人工或固定测试驱动器触发，不代表 AI 已经会规划。

**允许范围**：

- 建立 CB2.0 独立构建及运行时身份；记录游戏版本、模块列表、构建标识与实际加载 DLL 的一致性，明确区分 CBATH、旧 CombatBrain 和 CB2.0。
- 建立可刷新的双方 Formation 共享状态，并以独立采样检查人数、兵种、位置、状态及刷新时效。旧版暴露过的敌我混淆、兵力重复计数、预备队误判必须纳入针对性检查。
- 建立独立于 CB 决策日志的战场与命令效果观测。CB 自身写令可精确记录；外部命令若缺乏足够证据，标为“来源未判定”，不得推断为某个原生子系统。
- 验证最小 Formation 命令通路、原生覆盖情况及控制权归还。优先用一项可观察的命令域证明通路；其他域分别记录“已验证／未验证／受阻”。
- 对接现有功能草案的 CB-001、CB-014 与 CB-002 的最小部分。执行 FD-PoC P1/P2；采用 Route A 时验证 FD-PoC P11。其他引擎签名或时序 PoC 按实际触及的命令域执行，不把未经验证的域算作可用。

**非目标**：作战计划、兵种战术、机会利用、胜负评分、完整的原生命令来源分类。

**Exit Gate**：

1. 一场真实 CustomBattle 的记录能把 **运行构建身份 → 双方 Formation 状态 → 测试命令 → 战场实际命令／行动变化** 串在同一场次和时间线上；独立观测与 CB 自身日志分开保存。
2. 至少一次测试命令被证明确实作用于目标 Formation；若被原生系统改写，观测能识别“命令未持续生效”，不能仅凭 CB 调用日志宣布成功。
3. 玩家接管、租约结束或战斗结束时，CB 不继续抢令；相关控制权边沿有实机证据。FD-PoC P1/P2 的结论及适用命令域已记录；若关键命令域无法安全控制，停止向依赖该域的 P1 方案推进并回到设计评估。
4. 战场状态的刷新、敌我归属和人数统计通过独立核对；未能判断的字段明确标记，不以空值或旧快照冒充当前事实。

### P1 — 最小指挥闭环

**目标**：用最少的状态、评价和任务语义，让 CB2.0 从战场条件形成一个可执行的整体计划，并观察执行结果。这里的“闭环”仅包括基本生效与失效反馈，不要求成熟的战果利用或重规划。

**允许范围**：

- 建立最小己方能力与敌方态势判断，形成当前主要优势、威胁和目标；Plan 记录目标、理由、承担任务的 Formation、继续及失效条件。Plan 与具体 Order 分层。
- 至少让多个 Formation 的任务服务于同一目标。P1 只使用验证最小闭环所必需的任务类型，不一次做满功能草案的七类任务。
- 对发出的命令观察是否生效，以及计划所依赖的关键条件是否仍成立；条件失效时至少能停止或转入安全处置。完整的收益评估与重新规划留给 P3。
- 从第一次实际自动指挥起实施决策节奏、计划最小稳定时间和非零指挥延迟，并记录时间戳；具体参数待实机标定。紧急止损若需越过稳定时间，须有明确触发条件。
- 对应功能草案 CB-003～CB-007、CB-012 的**最小必需语义**及 CB-008 的基础反馈，不代表这些功能在 P1 已完整交付。胜利与控损均须进入初步判断；Charter §18 的 50/50 是当前概念权重，不在未经量纲与行为验证前硬写成 `0.5 × 胜利分 + 0.5 × 伤亡分`。

**非目标**：完整兵种角色库、复杂战果利用、主动试探、针对玩家的固定反制脚本。

**Exit Gate**：

1. 至少两种**关键条件不同**的战斗配置（如己方远程优势成立／不成立）产生可解释的不同目标或任务分配；改变输入后重新运行，不能仅改变 Plan 名称而保持同一套写令。
2. 每个自动命令均可追溯到同一个 BattleState 快照、Plan、Formation 任务与发令原因；独立观测证明命令实际生效或明确报告未生效。
3. 计划在条件未变时保持连续；当预设失效条件出现时能停止不合适的动作。时间记录证明没有逐 Tick 改主意，也没有全部 Formation 同时获得即时响应。

### P2 — 多 Formation 协同

**目标**：把 P1 的最小任务分配扩展为可处理多支部队和竞争命令的军队级指挥。

**允许范围**：

- 扩展通用任务语义与任务重新分配；任务不与固定兵种永久绑定。
- 对同一 Formation、同一命令域的竞争提案实行唯一裁决，并记录提案、拒绝或替换原因。执行层必须遵从当前 Plan 和任务权限；必要的安全接管属于显式规则。
- 验证主力、辅助和保护力量之间的协同，覆盖 Formation 损失或职责变化后的任务调整。
- 对应功能草案 CB-007 和 CB-002 的协同与仲裁部分；P0 已建立的基本安全仲裁持续有效。

**非目标**：为步、弓、骑、骑射各建一套独立战略；把任务枚举数量当作协同成果。

**Exit Gate**：

1. 在至少三支己方 Formation 参与的场景中，能从同一 Plan 解释主力、辅助与保护任务，且独立观测支持这些任务确实被执行。
2. 注入相互冲突的命令提案后，最终生效命令符合事先定义的 Plan／任务权限；不存在多个模块交替覆盖同一命令的持续抢令。
3. 移除、削弱或改变一支关键 Formation 后，其他任务能更新或明确报告当前计划不可执行，而不继续执行失去前提的旧命令。

### P3 — 反馈、止损与重规划

**目标**：根据行动实际结果判断继续、加大投入、改变执行方式或退出，让计划能够随战局更新。

**允许范围**：

- 为行动定义可观测的预期效果与成本，并用相同维度记录实际结果；正、负反馈均进入共享评价。
- 在正反馈下判断是否扩大局部优势；在损失、威胁或前提变化时止损。重规划有原因、时间与旧／新 Plan 关联。
- 把胜利机会与己方损失作为共同评价目标，检验选择是否符合 Charter §18 的取舍原则；公式、量纲和阈值须在本阶段验收前明确，不凭“50/50”字面值认定行为合理。
- 对应功能草案 CB-008、CB-009、CB-012 的深化。

**非目标**：把每次兵力变化都触发为重规划；主动诱导对手犯错。

**Exit Gate**：

1. 正反馈用例：行动产生可观测局部优势后，AI 基于该变化继续或追加合理任务，而非自动恢复静态；日志能关联观测与决定。
2. 负反馈用例：原目标失去价值、敌方有效反制或己方损失显著增加后，AI 在既定决策节奏内调整或终止 Plan，并停止旧 Plan 不再适用的命令。
3. 对照运行中若只改变上述关键反馈，后续决策应随之改变；若未改变，必须能说明继续原计划的判据。正、负样例均以实际战场观测核对。

### P4 — 主动权与战术博弈

**目标**：当等待无法带来有利机会时，AI 能选择有限行动改变局势，观察对手反应并据此决定后续投入。

**允许范围**：

- 在现有状态、评价、Plan、任务与反馈机制中加入试探型候选行动及退出条件，不为单个兵种或目标另建独立战术系统。
- 用可控对手先验证“施压 → 对手变化 → 我方识别”的可观测性；执行功能草案 FD-PoC P10。若原生 AI 不作出特定反应，记录适用条件，不把这一种对手行为当成 Charter 能力唯一实现路径。
- 验证玩家或受控对手的部署变化能进入判断，并改变行动价值与后续计划。对应功能草案 CB-010；CB-011 是否需要独立实现由实际变化检测缺口决定。

**非目标**：依赖固定脚本阶段切换伪装“试探”；假设任何对手都会按预定方式回应。

**Exit Gate**：

1. 有反应与无反应两组对照中，AI 的后续选择取决于实际观测到的变化；改变反应方式后，后续目标或投入也相应改变。
2. 至少一次完整记录可追溯 **采取行动 → 对手反应 → 战场状态变化 → 价值重评 → 后续计划**，并能排除只按计时器进入下一脚本阶段。
3. 试探失败或代价过高时，P3 的止损机制仍能终止行动。若关键反应无法稳定观测，阶段不能按通过处理，须记录受限场景并重新审查该能力的实现路径。

### P5 — 泛化与稳健性

**目标**：检验已形成的指挥循环能否跨场景工作，并处理暴露出的通用能力缺口。

**允许范围**：

- 建立场景矩阵，覆盖兵力比、兵种组成、Formation 数量、攻防身份、玩家部署变化和战斗中结构变化；前阶段的验收场景持续回归。
- 对每个失败先定位状态表示、评价维度、计划候选、任务语义、执行或反馈中的缺口；有证据证明通用机制无法表达时，才按 Charter §21/§26 审查专用系统。
- 地形与站位能力仅在矩阵显示其确为决策缺口时进入实现；若使用功能草案 CB-013 的可行走性子项，先完成相应 FD-PoC P3。

**非目标**：每出现一个失败场景就新增战术模块；无失败证据地做完功能草案中的全部候选项。

**Exit Gate**：

1. 场景矩阵、各配置的构建与运行条件、结果及失败归因可复查；至少覆盖上述每一类变化，允许一个场景同时覆盖多类。
2. 对导致目标能力失效的场景，要么以通用机制修复并通过回归，要么明确列为未解决限制；未解决限制不得被“其他场景通过”抵消。
3. 新增能力可说明其对应的 Charter 目标、通用机制缺口和回归证据，且未引入无关的情形专用规则链。

### P6 — Charter 最终体验验收

**目标**：判断 CB2.0 是否达到 Charter §3、§4、§22～§25 所要求的玩家对抗体验。

**允许范围**：

- 在正式实验前固定对手条件、玩家水平或测试方法、地图与兵力配置、样本量、胜负与伤亡指标，以及“通过”的判据。判据尚未确定时，P6 保持未通过。
- 用相同配置对比 CB2.0、原版及可用的旧 CombatBrain；对照组用于解释差异，Charter 的玩家对抗目标仍须单独验收。
- 审计关键战斗决策与结果的关系：玩家能否辨认整体意图，AI 是否利用实际漏洞，胜负是否主要由指挥选择而非隐藏 Buff、额外规则优势或测试配置差异造成。
- 在失败场次定位属于 P0～P5 哪一环的缺口，修复后重复受影响的阶段门槛与 P6 对照，不用调参掩盖未闭合能力。

**非目标**：靠挑选单场胜利宣称完成；以“模块都存在”代替实战体验；为通过验收引入不公平优势。

**Exit Gate**：预先确定的实战判据达到要求，行为审计能够解释关键胜负因素，且不存在违反 Charter 核心约束的证据。结果不达标、样本不足或判据事后改变，均不得标记通过。

## 4. 当前起点与第一张开发单

- **已知**：CBATH Phase 1 报告记载测试 Mod 身份、Formation 快照和连续进入／退出战斗的实机样本；这些证据的作用域仅限 CBATH 自身。其报告还列有启动入口、编排与固定战斗配置等剩余风险。
- **未验证**：CB2.0 模块加载身份、CB2.0 命令实际生效、命令来源精确归因，以及功能草案 FD-PoC P1～P11 的实验结论。功能草案中的 `VERIFIED` 多指 API／符号／机制证据，不能自动等同于本路线图的运行时 Exit Gate 通过。
- **建议首单**：以 P0 为范围，交付“CB2.0 可加载且身份可核对、双方 Formation 状态独立核对、最小命令通路与控制权边沿可观测”的实机证据。派单前明确测试构建、使用的命令域、FD-PoC 前置项和记录格式。

## 5. 依据与维护

- 上位目标：`Charter V0.2.md`，尤其 §3～§4、§7～§8、§11～§18、§21、§23～§27。
- 功能与技术风险对照：`CombatBrain-2.0-Feature-Decomposition-Draft.md` v0.2；该文件仍为草案，CB 编号、可行性标签与 FD-PoC 结论不得脱离其证据限定使用。
- 测试工具现状：CBATH 的 `12-Phase1-Implementation-Report.md` 与 `14-Phase1-Remaining-Risks.md`，均为 2026-09-24 的文档快照；启动 P0 时应核对当时的工具与构建状态。
- 本路线图变更阶段目标或 Exit Gate 时，应注明改变了哪项 Charter 目标、原阶段证据及对后续阶段的影响；不能用任务卡暗中放宽门槛。
