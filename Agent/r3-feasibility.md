## 0. 总体结论（一句话 + MVP 建议）

**结论：这套草案在架构方向与技术路径上可行，可以落地；但存在一个阻断级实测前提（CB-002 的 Route B 覆盖风险，须 S1 启动前实测闭合），且 CB-011 应降格、CB-010 须与 CB-011 解耦，否则 S3 会被最高难度模块拖死。**

**最小可交付集（MVP）= S1 + S2 闭环**：CB-001、CB-002、CB-003、CB-004、CB-005、CB-006、CB-007、CB-008。这 8 项闭合宪章 §27 的"理解己→理解敌→形成计划→分配任务→按节奏下达→观察战果评价"最小决策环，且全部不依赖任何"游戏不给权限"的能力、不越界单兵层（§20）、符合通用机制优先（§26）。CB-009/010/012/013 为增强项，CB-011 为可选/降格项，不进 MVP。

**决断性前提**：若 S1 前实测确认 `SetControlledByAI(false)` 后原生 Facing/Arrangement 仍持续覆盖、且 fail-open 短租约兜底不足，则必须启用 Harmony 拦 `OnBehaviorActivatedAux`（RBM 已证明其可行，且拦"命令重设"不触碰单兵定位数学，不违反 §20）——该方案应作为 Plan B 预先备好，不视为红线违反，而是命令收口的必要手段。

## 2. 风险登记册（按严重度排序）

### 🔴 阻断级
**R-01 Route B 覆盖风险未闭合（对应 CB-002 / §7 问题1）**
- 严重度：阻断（若失败，朝向/阵型控制不可靠，宪章 §9/§19 部分能力落空）。
- 证据：r1-glue §2 风险②"ATC-5R 实测提示 `SetControlledByAI(false)` 后原生 Facing/Arrangement 仍可能持续覆盖"；RBM 逐 patch `OnBehaviorActivatedAux` 佐证。
- 缓解：① S1 启动前**必须实机实测**租约内（TTL 1.25–1.5s）是否真被覆盖；② hybrid 短租约 + fail-open 自动归还 + 玩家接管立即释放作第一兜底；③ 若实测失败，启用 Harmony 拦 `OnBehaviorActivatedAux`（RBM 已证可行；拦"命令重设"不触碰单兵定位数学，不违反 §20，不视为红线违反）；④ 最坏情形下，Facing/Arrangement 降级为仅 Route B 关键命令表达，Movement 主路仍由 Route A 软注入保底。

### 🟠 高级
**R-02 指标自证为伪（对应 CB-008 / §7 问题7）**
- 严重度：高（旧版 `OrderTrace` 把内部 `Record` 误标"原生覆盖"，三场数据全废，r1-legacy §4 教训2）。
- 缓解：设计**不依赖 CB 内部 `Record` 的独立观测**——帧级 Formation 指令溯源（读 `Formation` 当前 Order 与 `IsAIControlled` 边沿），由独立于决策栈的观测器记录"该帧命令源 = CB 网关 / 原生 / 玩家"。在 S1 验收口径中强制写入（r2 §6 S1②）。

**R-03 CB-011 验收缺失（对应 §7 问题5）**
- 严重度：高。
- 缓解：降格为变化检测器（见 §1），验收标准改为"玩家 Formation 显著位移/转向/任务变更能被检测出"（可客观测），而非"推断玩家意图正确率"。若坚持做推断模型，须建离线标注"玩家部署→意图"数据集做回归，否则不得进范围（§21 四问第6条"仅增复杂度未成有效决策能力"）。

**R-04 感知 bug 重演（对应 CB-001/004/005）**
- 严重度：高（旧版 ATC-4 四个 P0 全为自身缺陷，r1-legacy §4 教训3）。
- 缓解：CB-001/004/005 共用刷新逻辑，须独立验证"刷新时效/敌我自反判定/兵力去重/预备队识别"四项，指标不可自证（复用 r2 离线回归工程，r1-code §3）。

### 🟡 中级
**R-05 节奏初值标定（对应 CB-003 / §7 问题6）**
- 严重度：中。决策间隔 N、稳定时间、MissionTimer 延迟、Route B TTL 初值需实机调，且与 §16"给玩家反制窗口"耦合。
- 缓解：初值取 IB 限流样板 0.8–1.5s（r1-glue §4）起步；以"玩家可观察到的反应窗口"为验收上限，不靠理论值。

**R-06 §18 伤亡量化（对应 CB-012 / §7 问题4）**
- 严重度：中。"伤亡"须定义可比较评价量。
- 缓解：明确公式 = `Formation 剩余兵力占比 × 历史损失速率`，作为 CB-008 反馈阈值与 CB-006 规划权衡输入；公式须在 MVP 阶段定稿，不可留空。

**R-07 地形精细判定（对应 CB-013 / §7 问题2）**
- 严重度：中。NavMesh 面类型细节未逐字核验。
- 缓解：MVP 仅用 `Scene.GetGroundHeightAtPosition` 高度差（已验证），可行走性/NavMesh 精细判定延至 S4 实测后补；不阻碍主体规划。

**R-08 重规划抖动（对应 CB-009）**
- 严重度：中。与 CB-003 最小稳定时间耦合。
- 缓解：重规划触发必须越过 CB-003 最小稳定时间；以 CB-008 正负信号或玩家显著变化为唯一触发源，禁每微变重规划。

### 🟢 低级
**R-09 竞态收敛（对应 CB-002 / §7 问题3）**
- 严重度：低（已定方向）。主线程 `OnMissionTick` 写令已吸收；若 patch `CreateNewOrderWorldPositionMT` 等 `_MT` 方法须 `TWSharedMutexReadLock`（r1-glue §3）。
- 缓解：命令读写全收敛主线程；按 Team 过滤加锁仅作 patch 时的兜底。

## 3. 阶段与依赖审计（B）

### 3.1 现状 4 阶段划分
| Stage | 成员 | 职责 |
|---|---|---|
| S1 基础底座 | 001/002/003 | 能观察 + 能下达 + 有节奏 |
| S2 决策闭环 | 004/005/006/007/008 | 闭合最小决策环 |
| S3 博弈深化 | 009/010/011 | 重规划 + 主动博弈 |
| S4 高级能力 | 012/013 | 权衡 + 地形维度 |

### 3.2 依赖关系核查
- 形式依赖（CB-002←001、003←002、004/005←001、006←004/005、007←006/002、008←001/002、009←006/008/003、011←001/005、012←004/005/008、013←001）**全部成立，无显式循环依赖**。
- **软耦合缺陷**：r2 将 CB-010 依赖声明为 `007/008/011`，把 CB-011（最高难度 + 质量待实测）列为 CB-010 的前置。这是**过度前置 + 软循环风险**：若 CB-011 在 S3 不达标，CB-010 的"观察敌反应判断"无法完成，S3 博弈深化被卡。
  - **建议调整**：将 CB-010 对 CB-011 的依赖**解耦**——试探效果改由 CB-008 战场状态前后 diff 判断（r2 §4 CB-010 本身已写"观察结果经 CB-008/CB-011 判断"，应明确优先 CB-008）。CB-011 仅作为 CB-010 的可选增强，不作为硬前置。
- **阶段排序偏误**：CB-011 难度标"最高"却排 S3 与 CB-009/010 平级，构成 S3 核心风险。
  - **建议调整**：CB-011 **降格为 S3 可选 / 可延后项**，S3 博弈深化主体由 CB-009（重规划）+ CB-010（试探）+ CB-008/007（反馈落地）承担，CB-011 仅作增益。这样即使 CB-011 质量不达标，S3 仍可验收（§6 S3②"主动制造局部压力并观察玩家反应"可由 CB-008 diff 满足）。
- **过度前置检查**：无功能被排得过早缺输入。CB-013 仅依赖 001 却排 S4，偏晚但合理（地形是增强维度，不阻塞主环）。
- **阶段跳跃检查**：S2 验收"行动结束有评价不自动恢复静态"（§6 S2）依赖 CB-008，CB-008 在 S2 ✓；"围绕统一 objective 组织行动"依赖 CB-006+CB-007，均在 S2 ✓。无阶段跳跃。

### 3.3 调整建议汇总
1. CB-010 解除对 CB-011 的硬依赖，改以 CB-008 为主判断源。
2. CB-011 降格为 S3 可选/延后，不进 MVP，验收标准改为变化检测。
3. 维持 S1→S2→S3→S4 顺序；S1 内 CB-002 的 Route B 实测必须先于 003 调参与 S2 启动。

## 4. 关键阻断项专项回答（C，逐条闭合 §7）

**Q1. Route B（`SetControlledByAI(false)` + 主线程写令）的指令被原生 AI 覆盖风险，能否可靠规避？**
→ **【必须 S1 前实测】**。判定：风险真实存在（r1-glue §2 风险②，ATC-5R 实测提示 + RBM 逐 patch 佐证），**不能断言已可靠规避**。当前 hybrid（Route A 主路 + Route B 窄保险丝短租约 TTL 1.25–1.5s + fail-open + 玩家接管即释放）对 **Movement 域足够**（Route A 已表达意图）；但对 **Facing/Arrangement 域**（Behavior 不走此域）若 Route B 租约内仍被原生覆盖，则朝向/阵型控制不可靠。处置：S1 前实测租约内覆盖情况；若失败启用 Harmony 拦 `OnBehaviorActivatedAux`（RBM 证可行，拦命令重设不违反 §20）。**结论：可规避，但需实测确认，且须备 Plan B。**

**Q2. 命令写入必须收敛到主线程（异步 AI tick 跑 worker 线程）对架构意味着什么？**
→ **【已有结论】**。意味着必须做"决策计算"与"命令落地"分离：认知/评价/规划/任务/反馈可在任意线程/频率计算，但**唯一写令出口 = 主线程 `OnMissionTick` 的 CB-002 网关**。异步 `doAsyncAITick→TickOccasionally` 产出的任何结果只能作为决策输入，不能直接写编队。架构上 CB-002 即为此强制收口，与 r1-glue §3 竞态规避一致。无额外实测需求。

**Q3. 决策节奏 / 指挥延迟（§16）用什么计时手段最稳？**
→ **【已有结论】**。用 `Mission.Current.CurrentTime`（float 秒时间戳）+ `MissionTimer`（`TaleWorlds.Library`，支持 `Reset`/`Check`）做时间门控：高层规划每 N 秒一次、计划最小稳定时间、命令入队经 `MissionTimer` 延时落地、各编队错峰响应形成 Command Latency（r1-glue §4）。初值取 IB 限流 0.8–1.5s 样板，**调参待实测**（R-05），手段本身 `[已验证]` 最稳。

**Q4. 是否存在任何 CB-00X 属于"游戏不给权限和途径"而必须换实现路径？**
→ **【已有结论】无**。逐一核对：所有 CB 仅用 Formation 级公开 API（Route A/B 写 `Set*Order`、读 `QuerySystem`/`Team`/`Formation` 属性、`Scene` 地形高度），不触碰单兵层/OrderController/隐藏信息（r1-glue §5 七条"不能做"已由 CB-002/CB-003 吸收）。CB-013 的 NavMesh 可行走性是"细节待实测"非"无权限"。总设计师"不存在某 CB 被判定引擎不支持"的论断**成立**。

**Q5. NavMesh 可行走性（§7 问题2）** → 【可延后】。MVP 仅用高度差 `[已验证]`，精细判定 S4 实测补（R-07）。

**Q6. 竞态收敛（§7 问题3）** → 【已有结论】。主线程写令已吸收；patch `_MT` 方法加 `TWSharedMutexReadLock` 作兜底（R-09）。

**Q7. §18 伤亡量化（§7 问题4）** → 【可延后但须 MVP 定稿】。公式须 S2 阶段明确定义（R-06），不可留空。

**Q8. CB-011 验收（§7 问题5）** → 【必须 S1 前定方案 / 否则降格】。见 R-03 与 §1 降格处置。

**Q9（补充）. 独立验证方案（§7 问题7）** → 【必须 S1 前定稿】。见 R-02，帧级 Formation 指令溯源观测器，独立于决策栈。

**Q10（补充）. RBM 对比实验（§7 问题8）** → 【可延后至 S2/S3 验收】。设计"只做 Formation 层 vs RBM 行为层"对照，作为下限标定（r1-rbm §5 建议3），非上限目标；实验条件须避免旧版"D 组零 Acquire"式过窄设计（r1-legacy §4 教训4）。
